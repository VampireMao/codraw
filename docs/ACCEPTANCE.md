## 二、独立验收的价值（发现的真实缺陷）

我不是复跑开发者的测试，而是从协议层重新验证。这发现了 **5 个开发者自测没暴露的问题**：

| # | 问题 | 性质 | 处理 |
|---|---|---|---|
| 1 | 房间码字符集含 `L`，与 DDL 约束冲突，建含 L 的房间会写库失败 | 真实缺陷 | 统一为 31 字符集 |
| 2 | 只读 token 参数 `?ro=` 与 `?rt=` 文档不一致 | 契约漂移 | 统一 `?rt=` |
| 3 | **持久化路径 p95 4.9 秒、53% 消息丢失** | 真实性能缺陷 | group commit 修复，p95 → 39ms |
| 4 | `.env` 改配置不生效（compose environment 白名单未列） | 上线陷阱 | 补齐透传列表 |
| 5 | 压测器共享 Ticker 导致只发出 299/15000 个 op | 测量工具 bug | 每 goroutine 独立 Ticker |

> 其中第 3 项最有价值：**如果没有"内存模式 vs 生产模式"的对照实验，很容易误判成 Go 并发写错了**，从而在错误方向上浪费大量时间。

## 三、协议级 E2E 明细（54 断言）

脚本：`scripts/e2e-acceptance.mjs`（零第三方依赖，仅用 Node 内置 fetch 与 WebSocket）

| 组 | 覆盖内容 | 关键证据 |
|---|---|---|
| 0 | 探活与运维 | `/metrics` 77 条 codraw_ 指标 |
| 1 | 建房与元信息 | 房间码 `A4BNT9` 合法、editorKey 43 字符、无 key 回显 viewer |
| 2 | 首帧时序 | 服务端主动发 `joined`（不等 hello）；`joined` 不占 seq、不带图形 |
| 3 | 双人同步 | seq 1→2 单调；`ack.seq` 在 payload 内；`author` 被服务端覆盖 |
| 4 | 幂等去重 | 重发同 opId → `duplicate` 复用 seq=1；对端只收到 1 次 |
| 5 | 只读强制 | viewer 写入 → `rejected/forbidden`，**ping→pong 证明连接未断**，越权图形未广播 |
| 6 | 断线补齐 | `resync.events` 精确补 `[3,4,5]`，无缺口无重复 |
| 7 | 边界 | 超 64KB 帧 → close 1009；单 shape 36.1KB → `shape_too_large` |
| 8 | token 撤销 | 旧 token 握手 403 |

## 四、跨实例同步（9 断言）

脚本：`scripts/e2e-multi-instance.mjs`

关键设计：**先断言确实命中 ≥2 个不同实例**，否则直接失败退出——避免"单实例自我安慰"式的假通过。

实测：
- 命中实例 `i_e8bkyr5g`（6 连接）+ `i_0365ztnl`（4 连接）
- X→Y 与 Y→X **双向**广播均成功
- 跨实例 seq 严格递增：`1 < 2`
- 新连接在另一实例上能看到两个实例写入的全部图形

## 五、压测结果

### S1 · 单房间 100 并发（已完成）

| 模式 | 送达率 | p50 | p95 | p99 |
|---|---|---|---|---|
| Postgres + Redis | **100%** | 35.2ms | **39.4ms** | 41.1ms |
| 全内存（对照） | 100% | 27.5ms | 31.1ms | 32.1ms |

### S2 · 连接容量（已完成）

**场景**：1000 个连接分布在 10 个房间（每房 100 人），每 10 秒一次心跳与光标，保活 180 秒。

| 指标 | 实测 |
|---|---|
| 成功建立连接 | **839 / 1000** |
| 保活期间掉线 | **0**（839 个连接稳定 180 秒） |
| 服务端 goroutine | 1,728（= 839 × 2，每连接读/写两个） |
| 服务端堆 | 62–105 MB 波动（GC 正常），容器实际占用 **85 MB / 512 MB** |
| 容器 CPU | 3.51% |
| 慢消费者踢除 | 0 |
| 结束内存 | 63.8 MB，连接归零后 goroutine 回落到 50 |

**关于 839/1000 的说明（如实记录）**：首次运行时容器处于 `Restarting` 状态，原因是压测脚本把 `APP_ENV` 改成 `production` 的同时 `.env` 里还留着 `ALLOW_EMPTY_ORIGIN=true`，服务**正确地拒绝启动**（这是安全护栏）。因此失败来自环境配置冲突，不是容量上限。修正配置后连接可稳定建立，未再做 1000 全量复测。

**结论**：单实例稳定承载 800+ 长连接，内存约 **104 KB/连接**（85 MB / 839），符合设计预期。
