## 2. S1 · 单房间 100 并发绘制（核心指标）

**场景**：1 个房间，100 个客户端，每客户端 5 op/s，持续 30 秒，全部绘制。合计约 15,000 次写操作，产生约 150 万条广播。
**延迟定义**：客户端 A 发出 op 的时刻 → 客户端 B 收到该 op 的时刻（同进程内共享时钟，无需 NTP 对齐）。

### 生产模式（Postgres + Redis）

| 指标 | 值 |
|---|---|
| 发送 op | 14,978 |
| ack 数 | 14,978（**100% 确认**） |
| 收到广播 | 1,497,800 / 1,497,800 |
| **送达率** | **100%** |
| p50 | 35.2 ms |
| **p95** | **39.4 ms** |
| p99 | 41.1 ms |
| 错误 / 意外断开 | 0 / 0 |
| 慢消费者踢除 | 0（与日志一致） |
| 服务端堆 | 448 MB（1.5 万个 shape 对象） |

### 内存模式（对照）

| 指标 | 值 |
|---|---|
| 送达率 | 100% |
| p50 / p95 / p99 | 27.5 / 31.1 / 32.1 ms |
| 服务端堆 | 97 MB |

> **结论**：持久化只带来约 8 ms 的 p95 代价。批量提交（group commit）让"先落库再广播"的语义在 500 op/s 下依然成立。

## 3. 优化前后对比（这是本项目最有价值的一段）

### 问题现象

第一版实现里，每条 op 都在房间 goroutine 内**同步等待**一次 DB 写入；Redis 模式还要额外做 `INCR`（分配 seq）与 `PUBLISH`（跨实例广播），合计 3 次同步往返。

| 指标 | 优化前（Postgres + Redis） |
|---|---|
| 送达率 | **47%**（703,800 / 1,498,000） |
| p50 | 4,441 ms |
| p95 | **4,894 ms** |
| 服务端堆 | 343 MB |
| 日志 | 大量 `evicting slow consumer` |

500 op/s × 3 次往返 = 1500 次/秒的同步 IO，房间 goroutine 被完全占满，出站队列溢出，53% 的消息被丢弃。

### 定位过程

关键实验：**同一压测脚本，只切换 `STORE`/`BROKER`**。

- `memory + memory`：p95 = 80 ms，送达率 100%
- `postgres + redis`：p95 = 4,894 ms，送达率 47%

对照组证明瓶颈**不在房间并发模型、不在 WebSocket、不在广播扇出**，而在持久化写入路径。如果没有这个对照实验，很容易误判成"Go 并发写错了"。

### 修复手段

1. **批量提交（group commit）**：房间 goroutine 用 `select` 攒批（窗口 20 ms / 上限 256 条），一次 `AppendBatch` + 一次 `PublishOpBatch`。500 次/秒的往返压到几十次。
2. **seq 批量分配**：Redis 模式用 `INCRBY key N` 一次拿一段连续区间，本地分配，仍然严格单调无空洞。
3. **修掉 O(n²)**：`publishStats` 每次 op 都遍历全图统计图形数，改为增量维护 `liveShapes` 计数器。**这一项单独把房间吞吐从 943 op/s 提到 7,938 op/s（8.4 倍）**。
4. **慢消费者通知**：`Kick` 改为直接写 close 帧（gorilla 允许控制帧并发写），不再排在已堵死的写泵后面——被踢的客户端**确实收到 4001**，而不是"踢了但没通知"。

### 修复后

| 指标 | 优化前 | 优化后 | 改善 |
|---|---|---|---|
| 送达率 | 47% | **100%** | +53 个百分点 |
| p50 | 4,441 ms | **35.2 ms** | **126×** |
| p95 | 4,894 ms | **39.4 ms** | **124×** |
| 慢消费者踢除 | 大量（指标漏计） | 0（指标与日志一致） | — |

## 5. 已知限制（面试主动说）

| 限制 | 说明 |
|---|---|
| 内存随图形数增长 | 30 秒 1.5 万图形 → 448 MB。长跑依赖快照 + 裁剪，不是无界缓存 |
| 单房间图形上限 2 万 | 超出返回 `room_full_shapes`，压测 45 秒以上会触发。这是保护机制，不是 bug |
| 20 ms 批量窗口 | 极低负载（<10 op/s）下单个 op 最多多 20 ms 延迟，仍在预算内；可优化为"无 pending 时立即 flush" |
| 同机压测 | 真实公网 RTT 会显著高于此，务必声明 |
| 单实例验证 | 跨实例同步已单独验证功能正确，但未做双实例压测 |
| 连接容量 | 实测稳定 839 连接 / 85 MB（约 104 KB/连接），未做 1000 全量复测 |

## 6. 测量方法上的两个坑（值得讲）

**坑一：压测器自己成为瓶颈。**
第一版压测器用 Node 写，单线程 JS 解析 5 万条/秒入站广播时扛不住，测出 p50 = 28 秒的荒谬数字。改用 Go（每连接一个 goroutine 并行解析）后才有可信数据。**测出来的数字不对时，先怀疑测量工具。**

**坑二：共享 Ticker。**
第二版压测器让 100 个 goroutine 共享一个 `time.Ticker`，但 Ticker 的 channel 只能被一个 goroutine 收到，实际只发出 299 个 op（设计 15,000）。修复为每 goroutine 独立 Ticker 后才达标。**并发的基准测试本身就是并发程序，同样会有并发 bug。**

**坑三：改了代码没重新构建就测。**
中间多轮"修复无效"的测量，实际跑的都是旧二进制。`go build` 之后必须重新启动进程，否则测的还是旧版本。这类问题不报错，排查成本极高。
