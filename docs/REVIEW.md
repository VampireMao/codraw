## 五、架构层面的价值点（面试可讲）

### 5.1 三个真正的技术深度

| 点 | 为什么值钱 |
|---|---|
| **每房间单 goroutine** | 房间内零锁，seq 顺序是结构保证而非纪律；跨房间天然并行 |
| **批量提交（group commit）** | 真实优化：p95 从 4894ms → 39ms，**124 倍**。有完整的定位过程 |
| **单调 seq + pending 队列 + opId 幂等** | 断网 60s 零丢失零重复，三个条件缺一不可 |

### 5.2 三个真实的取舍（有 ADR 支撑）

| 取舍 | 代价 | 为什么接受 |
|---|---|---|
| 不上 CRDT | 并发编辑同图形靠 LWW | 白板冲突密度极低，省下整个 CRDT 复杂度 |
| `editorKey` 不再是编辑权 | 老链接需手动授权 | 「房主独占」的必要条件 |
| 页面重载拉全量快照 | 每次几 KB 流量 | 持久化 shapes 要处理版本一致性，成本远高 |

### 5.3 三次真实的 bug 定位（最有说服力的故事）

| Bug | 根因 | 教训 |
|---|---|---|
| 实时同步失效 | `shallowRef` 就地修改不触发浅监听 | 协议层全绿 ≠ 用户看得见，必须像素级验证 |
| 重做失效 | 撤销发 `delete`，重做发 `update` 命中墓碑 | 每次发 op 都要问「服务端认为它是什么状态」 |
| 重进丢内容 | `appliedSeq` 持久化了但 shapes 没有 | 持久化必须成对，否则状态自相矛盾 |

> 这三个都**不是靠读代码发现的**，而是靠端到端验证。面试讲这个比讲功能列表有价值。

## 六、遗留风险与已知限制

### 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `STORE=memory` 重启丢数据 | 演示时重启即丢 | 用 `--store postgres`；或演示时不重启 |
| 单房间 2 万图形上限 | 极端场景被拒 | 保护机制，非 bug |
| 内存随图形数增长 | 1.5 万图形 448MB | 依赖快照裁剪，长跑需观察 |
| 多实例 seq 竞争 | 极端乱序 | 客户端 resync 兜底；已文档化 |

### 功能缺口（PRD 的 P1，未做）

- 导出 PNG/SVG
- 历史回放
- 激光笔
- 房间列表 / 账号体系

### 未验证项（诚实记录）

- **双实例压测**：功能验证过（`e2e-multi-instance.mjs`），性能未测
- **公网真实延迟**：同机测试，公网 RTT 会更高
- **移动端真机**：Playwright 模拟过，但没在真实手机上跑过
