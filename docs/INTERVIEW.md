## 1. 90 秒电梯陈述（背下来）

> 我做了一个实时协作白板，叫同绘 CoDraw。打开链接就能多人同时画，PC 和手机同一套代码，断网还能继续画、恢复后自动补齐。
>
> 技术上它是**单二进制 Go 服务**：每个房间是一个独立 goroutine，独占房间状态，自己分配单调递增的序号，把操作广播给房间里的所有人。没有锁竞争，也没有跨房间的耦合。前端是 Vue 3 + Canvas 2D，操作先本地乐观渲染，服务端确认后转正。
>
> 有两条我比较在意的：**序号机制**保证断网 60 秒重连后零丢失、零重复；**只读权限在服务端强制**，不是前端把按钮藏起来。
>
> 一条命令起单机，也可以起两个进程，用 Redis 做跨实例广播，客户端无感。而且它**就是一个可执行文件**——前端已经编译进去了，不需要 Node、不需要 Nginx、不需要容器。
>
> 压测里 100 人同房间同时画，广播 p95 是 **39 毫秒**，150 万条广播 100% 送达。这个数字不是一开始就有的——最初接上 Postgres 后 p95 掉到 4.9 秒、一半消息被丢，我用对照实验定位到是每条 op 都在房间 goroutine 里同步等一次 DB 写入，改成批量提交后回到 39 毫秒。

## 3. 高频追问与应答

### 3.1 为什么不用 CRDT？

> 白板的冲突密度极低——两个人同一毫秒改同一个矩形的情况基本不存在。CRDT 能换来"离线也能完美合并"，代价是要引入 Yjs/Automerge 这类库、数据结构变得不可读、服务端要保存 CRDT 状态、调试成本陡增。
>
> 我选的是**服务端权威事件日志 + LWW**：所有写进一个有序日志，seq 单调，冲突时后到者赢。对白板这个场景，用户感知的差异几乎为零，但我省下了整个 CRDT 的复杂度，还能天然支持历史回放和审计。
>
> 如果需求变成"离线编辑一整天的文档再合并"，我会换 CRDT——这是场景决定的，不是技术优劣。

### 3.2 断线 60 秒，凭什么保证零丢失零重复？

分三件事，缺一不可：

1. **不丢**：本地操作先进 IndexedDB 的 pending 队列，再上屏渲染。网络断了队列还在，用户继续画就继续入队。
2. **补齐**：每条持久消息带房间级单调 `seq`，客户端记录 `appliedSeq`。重连时发 `hello{lastSeq}`，服务端只补 `lastSeq` 之后的。如果 `lastSeq` 已经超出服务端保留窗口，就退化成全量快照。
3. **不重复**：每个操作带一个客户端生成的 `opId`，服务端维护 `(clientId, opId)` 去重窗口，重放同一条返回 `ack{duplicate, 首次seq}`，不产生第二个图形。客户端也按 `opId` 判重。

> 关键点：**重放必须复用原 `opId`**。换个 id 就会真的产生重复图形——这是这套机制唯一的坑，我在协议里写死了。

### 3.3 房间 goroutine 模型，会不会成为瓶颈？

> 单房间的所有状态只被一个 goroutine 访问，所以房间内部**零锁**。100 人在一个房间里画，瓶颈在扇出（1 条消息广播 100 次）和网络，不在锁竞争。
>
> 真正要防的是**慢消费者**：一个人网络差，发送队列积压，如果阻塞写就会拖垮整个房间。所以每条连接一个有界队列（256），投递用非阻塞 `select`，满了就踢掉这条连接（关闭码 4001），其他人完全不受影响。
>
> 跨房间天然并行——每个房间一个 goroutine，多核自动扩展。

### 3.4 seq 是单实例内存自增，两个实例怎么办？

> 用 Redis `INCR` 按房间分配，key 是 `codraw:seq:{room}`，保证跨实例全局单调。代价是每条消息多一次 Redis 往返——本地实测 p95 <在此填>。
>
> 这是个明确的取舍：单实例模式下 seq 是内存自增，零延迟；开 Redis 模式才有这次往返。两种模式用 `BROKER` 环境变量切换，本地开发和演示不付这个成本。

### 3.5 为什么是 Canvas 2D，不是 SVG 或 WebGL？

> SVG 每个图形是一个 DOM 节点，1000 条笔迹就是 1000 个节点，每次平移都要重排，手机上直接卡死。Canvas 2D 是立即模式，重绘成本可控，我用 rAF 合帧 + 分层缓存把 1000 条笔画的平移稳定在 60fps。
>
> 没用 WebGL：白板的图形量级（万级）不需要 GPU，WebGL 会引入着色器、纹理管理、上下文丢失恢复这些复杂度，收益不匹配。

### 3.6 只读链接凭什么"真只读"？

> token 是 HMAC-SHA256 签名的，载荷含房间和签发时间，服务端能独立验证，不查库。
>
> 撤销用**签发时间水位**：房间记录 `readonlyMinIssuedAt`，早于水位的 token 全部失效。这样撤销是无状态的，不需要维护黑名单。
>
> 权限判断在 hub 入口做，viewer 的 `op.add` 直接返回 `ack{rejected, forbidden}`，连接不断开。前端隐藏工具栏只是体验，不是安全边界。

### 3.7 消息格式为什么用 JSON，不用 Protobuf？

> 白板单条消息几十到几百字节，JSON 的体积和解析开销在这个量级不是瓶颈——压测里 5k msg/s 时序列化占比 <在此填>。
>
> 换成 Protobuf 能省带宽，但会失去"打开 DevTools 就能看懂协议"的调试便利，联调成本上升。我的判断是：**在瓶颈不在序列化的时候，可调试性更值钱**。如果带宽成为瓶颈，我会先上 zstd 压缩整个帧，再考虑换编码。

### 3.8 你怎么知道它真的能扛？

> 我写了个 Go 压测器，复用协议包直接跑真实握手和消息，不是拿 ab 打 HTTP 接口。
>
> 测了三组：单房间 100 并发持续绘制、单实例 1000 连接保活、5k msg/s 吞吐。数字和复现命令都在 README 里。`/ops` 面板能看到实时 p95。

### 3.9 上线后出问题怎么排查？

> 三层：`/healthz` 探活、`/readyz` 含依赖连通性、`/metrics` 是标准 Prometheus 文本格式。日志是结构化 JSON，带 request id 和房间码，能串起一次请求。
>
> 我特意没上 Prometheus + Grafana 全家桶——3 天工期里多两个容器就是多两处故障点。`/ops` 单页把关键指标直接暴露，面试现场反而更好演示。

### 3.10 这个项目最大的不足是什么？

> 三个，我知道得很清楚：
> 1. **没做真正的离线优先**：断网超过服务端保留窗口就退化成全量快照，房间很大时会慢。
> 2. **没做多白板页面和权限分级**：现在一个房间一块板，房主/访客两档，真实团队协作不够用。
> 3. **压测是单机单机房的**：没做跨可用区的网络延迟测试，真实公网下的 p95 会比本地差。
>
> 如果给我一周，我优先做第 1 条——它直接影响弱网体验。
