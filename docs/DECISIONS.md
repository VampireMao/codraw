# 产品决策记录（PM · 逐条可追溯）

> 面试官如果问「你为什么这么设计」，答案在这里；如果问「谁决定的」，也在这里。
> 格式：决策 → 理由 → 被否决的方案 → 何时该重新考虑。

---

## D1 · 实时同步用「服务端权威事件日志 + 单调 seq」，不用 CRDT/OT

**决策**：所有写操作进房间级有序日志，服务端分配 seq；客户端乐观渲染，靠 seq 补齐。

**理由**：白板冲突密度极低。CRDT 能换来完美离线合并，代价是引入 Yjs/Automerge、状态不可读、服务端要存 CRDT 结构、调试成本陡增。3 天工期里，正确性优先于理论优雅。

**被否决**：Yjs + y-websocket（现成但服务端变成黑盒，面试讲不透）；OT（需要中心化转换，复杂度和 CRDT 同量级）。

**何时重新考虑**：需求变成"离线编辑一整天的文档再合并"、或多人同时编辑同一段富文本。

---

## D2 · 每房间单 goroutine，房间内零锁

**决策**：房间状态只被一个 goroutine 访问，其他 goroutine 通过命令 channel 或 `Member` 接口交互。

**理由**：白板的读多写少、按房间天然分片。单 goroutine 消除了锁竞争和死锁可能，`shapes`/`members`/`seq` 都是无锁访问，代码可读性反而更高。跨房间自动并行。

**被否决**：全局 `sync.RWMutex` 保护所有房间（热点房间会拖垮全局）；分片锁（调优空间小，复杂度不划算）。

**何时重新考虑**：单房间超过 500 人且消息频率极高，单 goroutine 的扇出成为瓶颈——那时按"房间内再分片"演进。

---

## D3 · 出站队列有界 + 慢消费者剔除

**决策**：每条连接 256 容量出站队列，投递用非阻塞 `select`，满了直接踢（关闭码 4001）。

**理由**：一个网络差的用户如果阻塞写，会拖垮整个房间的广播。宁可踢掉一个人，也不能让 99 个人卡住。

**被否决**：无界队列（慢消费者导致 OOM，进程级故障）；阻塞写（一人卡全房间）。

**何时重新考虑**：如果踢人过于频繁，说明队列容量或业务消息量需要调整，而不是改成无界。

## D4 · Canvas 2D，不用 SVG / WebGL

**决策**：Canvas 2D + rAF 合帧 + 分层缓存。

**理由**：SVG 每个图形一个 DOM 节点，1000 条笔迹就是 1000 个节点，平移时重排直接卡死。WebGL 对万级图形是过度设计，还引入上下文丢失恢复等复杂度。

**被否决**：SVG（节点数爆炸）；WebGL/PixiJS（复杂度与收益不匹配）。

**何时重新考虑**：图形数稳定超过 5 万且需要复杂滤镜/混合模式。

---

## D5 · 单二进制 + `go:embed` 前端产物

**决策**：前端构建产物嵌进 Go 二进制，一个镜像对外提供服务。

**理由**：部署链路最短，没有 CORS、没有 Nginx 配置、没有静态资源版本错配。镜像 <60MB，冷启动快。

**被否决**：前后端分离部署（多一个服务、多一处故障点、多一套 CORS 配置）。

**何时重新考虑**：前端团队独立发版频率远高于后端，或需要 CDN 边缘缓存静态资源。

---

## D6 · 单实例零依赖可跑，Redis/Postgres 作为可选增强

**决策**：`BROKER=memory|redis`、`STORE=memory|postgres` 用环境变量切换，默认 memory。

**理由**：面试现场最怕"演示环境起不来"。零依赖模式 `go run` 就能跑，任何人 clone 下来 30 秒能看到效果。生产模式一行配置切过去。

**被否决**：强制依赖 Postgres/Redis（本地开发门槛高，演示风险大）。

**何时重新考虑**：从未——这个设计本身就是卖点。

---

## D7 · 只读权限服务端强制，且用无状态 HMAC token

**决策**：viewer 的写请求在 hub 入口被拒，返回 `ack{rejected, forbidden}` 且连接不断；token 用 HMAC-SHA256，撤销靠签发时间水位。

**理由**：前端隐藏按钮不是安全边界。无状态 token 不需要查库，撤销用 `readonlyMinIssuedAt` 水位实现，不需要维护黑名单。

**被否决**：数据库存 token 表（每次校验一次查询）；前端判断权限（可被绕过）。

**何时重新考虑**：需要细粒度权限（某人只能编辑某个图层）时，才需要真正的权限模型。

---

## D8 · 消息用 JSON，不用 Protobuf

**决策**：WebSocket 用 JSON 信封。

**理由**：单条消息几十到几百字节，序列化不是瓶颈。JSON 让 DevTools 直接可读，联调成本低。压测会给出真实数字证明序列化占比。

**被否决**：Protobuf（省带宽但失去可调试性）；MessagePack（同理，且生态不如 JSON 通用）。

**何时重新考虑**：带宽成为实测瓶颈时，先上整帧 zstd 压缩，再考虑换编码。

---

## D9 · 多实例用 Redis `INCR` + Pub/Sub，不做选主

**决策**：跨实例 seq 由 Redis `INCR` 分配，广播走 Pub/Sub。

**理由**：`INCR` 天然原子且单调，不需要引入 Raft/ZooKeeper。Pub/Sub 足够白板的扇出场景。极端乱序由客户端 resync 兜底。

**被否决**：选主 + 主节点分配 seq（故障切换复杂）；Kafka（对 3 天项目是杀鸡用牛刀）。

**何时重新考虑**：需要消息持久化与重放保证时，Pub/Sub 不够（它不持久化）。

---

## D10 · PWA，不做原生壳

**决策**：一套 Vue 代码 + PWA，覆盖 PC 与 Android 浏览器/安装态。

**理由**：3 天内单代码库覆盖全部目标端。Tauri/Electron 要额外工具链与打包时间；Android 原生要 JDK+SDK 约 5GB，风险收益不匹配。

**被否决**：Tauri（时间不够，且桌面端不是核心场景）；原生 App（工期风险极高）。

**何时重新考虑**：需要系统级手写笔压感、离线文件系统访问、或应用商店分发。

---

## D11 · 不做账号体系

**决策**：昵称 + clientId 存 localStorage，无注册无登录。

**理由**：面试场景下，任何登录墙都会劝退面试官。免注册是产品优势而非妥协。编辑权限靠 `editorKey`（创建时一次性返回）。

**被否决**：OAuth/邮箱登录（增加演示摩擦，收益为零）。

**何时重新考虑**：需要房间列表、跨设备同步、团队管理时。

---

## D12 · 便签用 HTML textarea 浮层，不在 canvas 里做文本输入

**决策**：双击画布弹出绝对定位的 textarea，失焦提交为图形。

**理由**：canvas 没有原生文本输入，自己实现光标、选区、中文输入法（IME）组合事件是深坑。textarea 天然支持 IME、复制粘贴、移动端键盘。

**被否决**：canvas 内自绘光标 + 隐藏 input（IME 兼容性差，中文用户直接废掉）。

**何时重新考虑**：需要富文本（加粗、列表）时，引入真正的内容编辑器。

---

## D13 · 3 天不做 Prometheus + Grafana 全栈

**决策**：`/metrics` 输出标准 Prometheus 文本（可被任何系统抓取），同时提供 `/ops` 单页面板。

**理由**：多两个容器就是多两处演示故障点。`/ops` 单页在面试现场反而更好展示——不用切 Grafana 登录。

**被否决**：Grafana 全家桶（演示风险 > 展示收益）。

**何时重新考虑**：真实生产环境必然接入，`/metrics` 已经为此准备好。
